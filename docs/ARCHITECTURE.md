# Architecture

This document describes how the code is organised **today**. The target architecture and the reasons behind it are in the [implementation plan](IMPLEMENTATION_PLAN.md#4-architecture). Individual decisions are recorded in [adr/](adr/).

## Overview

```
Browser (React app)  ──HTTP──────▶  Fastify server  ──▶  SQLite (memora.db in /data)
  IndexedDB           ◀─WebSocket─     │
  service worker                       │
        ▲                              │
        └──── static files ◀───────────┘  (the server also serves the built web app)
```

In production there is **one process in one container**. The server serves both the API (`/api/...`) and the built web app. Any unknown non-API path returns `index.html`, so client-side routes such as `/p/<id>` work when you reload the page. In the browser, pages being edited live in IndexedDB first, and a service worker keeps the app itself, so both work without a connection.

## Workspace packages

| Package           | Role                                                 | Built with                                    |
| ----------------- | ---------------------------------------------------- | --------------------------------------------- |
| `apps/server`     | HTTP API, database, migrations, startup and shutdown | esbuild → `dist/server.mjs`, `dist/admin.mjs` |
| `apps/web`        | Single-page app                                      | Vite → `dist/`                                |
| `packages/shared` | Schemas, types and pure helpers used by both sides   | Consumed as TypeScript source                 |

### Server bundle

The server is bundled together with `@memora/shared` and every pure-JavaScript dependency, into two entry points: the server and the `memora-admin` command-line tool. Only native modules stay external: `better-sqlite3` and `@node-rs/argon2`. They are the only entries under `dependencies` in `apps/server/package.json`; everything else is a `devDependency`. Both ship prebuilt binaries, so nothing is compiled, in CI or in Docker.

### Paths

The dev entry (`src/*.ts`, run by `tsx`) and the bundle (`dist/server.mjs`) both sit one level below `apps/server/`. `src/paths.ts` resolves `drizzle/` (migrations) and `../web/dist` relative to that, and the Docker image keeps the same layout under `/app`. As a result there are no absolute paths in code and no differences between environments.

## Startup sequence (`apps/server/src/index.ts`)

1. Read and validate the configuration from environment variables (`config.ts`, zod). Invalid values stop the process with a readable message.
2. If a backup waits to be restored (`restore/`, D35), put it in place of `memora.db`.
3. Read the instance key (`auth/secretKey.ts`, D47), making `secret.key` (mode 600) on first start. A damaged key stops the process with a readable message.
4. Open `memora.db` with the durability pragmas: WAL, `synchronous=FULL`, foreign keys.
5. **Migrations** (`db/migrate.ts`):
   - refuse to open a database written by a newer version (downgrade protection);
   - take a consistent backup before changing an existing database;
   - apply the pending Drizzle migrations.
6. Record the instance ID and the version that created the database in `app_meta`.
7. Listen, and start the backup schedule. If no account exists yet, print a one-time setup code to stdout (kept only in memory).
8. Every 6 hours, delete expired sessions, prune the audit log (a year, at most 50,000 entries), thin out page versions, purge the recycle bin, and delete files nothing uses any more.
9. On `SIGTERM`/`SIGINT`, close the server, then close the database, which checkpoints the WAL. After a restore was prepared, the same, but ending with exit code 75, for Docker's restart policy to start Memora again.

## Container

- **Multi-stage build.** A `node:24-bookworm-slim` stage builds everything. The runtime stage is `debian:bookworm-slim` plus the Node.js binary, the bundle, the web assets and `better-sqlite3`. It contains no npm, corepack or compilers.
- **`docker/entrypoint.sh`:**
  - caps the V8 heap (`MEMORA_MAX_HEAP_MB`);
  - prepares `/data`;
  - drops from root with `setpriv` to the data folder's owner, or to `PUID:PGID` when set (`docker/memora-user.sh`);
  - refuses to run as root;
  - never runs a recursive `chown` on existing data.
- **Health check.** The image's `HEALTHCHECK` calls `/api/health` every 60 s. The route logs only at warn level, so these checks don't flood the log.
- **`memora-admin`** (`docker/memora-admin.sh`) runs `dist/admin.mjs` as the server's user, even when `docker exec` starts it as root, so files it creates in `/data` keep the right owner.
- **Publishing.** After CI passes on `main`, `.github/workflows/publish.yml` builds the image natively on amd64 and arm64 runners, runs the smoke test on each, and pushes `:edge` and `:sha-<commit>` to GHCR as one multi-architecture image.

## Database

- **Schema:** `apps/server/src/db/schema.ts` (Drizzle ORM).
- **Migrations:** generated SQL in `apps/server/drizzle/`, created with `pnpm db:generate`, committed to git and applied at startup.
- **Backups:** `db/backup.ts` uses SQLite's online backup API. Backup file names avoid colons so they can be copied to any file system.

## Backups (`apps/server/src/backup`, `routes/backups.ts`, D34–D35)

- **`service.ts`** makes backups (one at a time), lists them from the file names, keeps the schedule with a single timer (`cron.ts`, local time, re-armed after each run), and prunes by age buckets after each scheduled backup: everything from the last day, then the newest of each of the last days, weeks and months (`MEMORA_BACKUP_KEEP`).
- **Encryption** (`envelope.ts`). With `MEMORA_BACKUP_PASSWORD_FILE`, a backup is written to a temporary file and encrypted into `…db.enc`: the `MEMORAENC1` header (with the scrypt salt and parameters and the nonce) is authenticated with the data by AES-256-GCM, so a changed byte anywhere fails to decrypt. Backups are streamed, not read into memory.
- **Restore.** `prepareRestore` decrypts or copies the backup into `restore/pending.db`, checks it, gives it a new data id, backs up the current state (`pre-restore`) and writes `restore/pending.json`. The route answers, then asks for a restart; `applyPendingRestore` puts the file in place at the next start, before the database opens. `memora-admin restore` prepares the same way and asks for `docker restart`.
- **API** (administrators only, audited): `GET /admin/backups` (list and status), `POST /admin/backups`, `GET /admin/backups/:name` (download), `DELETE /admin/backups/:name`, `POST /admin/backups/:name/restore`. Names are matched against the backup name pattern, so no other file can be reached.

## Authentication (`apps/server/src/auth`, `routes/`)

- **Layers.** `repo/` wraps the tables (users, sessions, audit log) and is the only code that queries them. `auth/service.ts` holds the rules: setup, login, sessions and password changes. `routes/` turn HTTP requests into service calls and validate every body with the zod schemas from `@memora/shared`, which the web app uses too.
- **Access gate** (`auth/plugin.ts`). Every `/api/` route declares `config.access`: `public`, `user` or `admin`. Registering a route without it stops the server at startup. One `onRequest` hook then applies the API rate limit, checks the origin of changes, resolves the session cookie, and enforces the route's access level, the CSRF token, a pending password change, and two-step verification when an administrator requires it (`allowPendingTwoFactor` marks the routes that set it up). Handlers can rely on `request.auth` being set when their route needs a user.
- **Sessions.** The cookie carries a random 32-byte token; the `sessions` table stores its SHA-256 hash, so a copy of the database can't be used to log in. Expiry slides with use; `last_seen_at` is written at most every 5 minutes. The CSRF token is an HMAC of the session token, so it needs no storage.
- **Passwords.** Argon2id through `@node-rs/argon2`, at most two hashes at a time, so a burst of logins can't use much memory. Unknown usernames still cost one hash, so response times don't reveal which accounts exist.
- **Two-step verification** (`auth/totp.ts`, `auth/twoFactor.ts`, D47). RFC 6238 codes on `node:crypto`; the step of the last accepted code is stored, so each code works once, even when two requests race. A right password with two-step verification on answers a ticket (in memory, five minutes, five tries), and `POST /auth/login/two-factor` turns ticket and code into a session. Secrets are sealed with AES-256-GCM under the instance key; recovery codes are stored as SHA-256 hashes. The "required" setting is in `app_meta`, cached in memory.
- **Headers** (`app.ts`, `@memora/shared` `security.ts`). An `onSend` hook adds the Content Security Policy and the other security headers to every answer; API answers get a policy that loads nothing. The web app's preview server sends the same, so the end-to-end tests run under the real policy. The web build starts zod without its `new Function` probe (`vite.config.ts`), which the policy would report.
- **Throttling** (`auth/throttle.ts`). In-memory counters per username and per address, and per account for two-step codes, with doubling delays, capped at 10,000 entries.
- **Tests.** `auth/access.test.ts` lists every API route with its expected access level and fails when a route is added without an entry, then checks anonymous, regular-user and cross-user requests against each one.

## Notes (`apps/server/src/notes`, `routes/notes.ts`)

- **Tables.** `notebooks`, `section_groups` (nested through `parent_group_id`), `sections` and `pages` (subpages through `parent_page_id`), plus `user_settings` for per-user UI state. Every row carries `owner_id`, and every query filters on it, so another user's ids simply aren't found (404).
- **Order.** Siblings are ordered by a fractional-index `sort_key` (`fractional-indexing`), compared as plain strings, so a move writes only the moved rows. `placeKeys` in `@memora/shared` computes the keys for "before this sibling, or last", and the web app uses the same function to show a move before the server answers.
- **Soft delete.** Deleting sets `deleted_at` on the item and `deleted_root_id` on it and everything inside, so restoring the root brings back exactly what went with it, and nothing deleted earlier. A restore is refused while the parent is itself in the recycle bin; a restored item whose place was taken gets a new key at the end.
- **Limits.** Groups nest at most four levels and pages three; moves that would go deeper, or inside themselves, are refused with `too_deep` or `invalid_move`. Moving a group or page to another notebook or section takes its subtree along, including rows already in the recycle bin.
- **Inbox.** Each user's inbox is a section outside any notebook (`is_inbox`, at most one per owner, created on the first `GET /tree`). It can't be renamed, moved or deleted.
- **API.** `GET /api/v1/tree` returns all page metadata (with a short snippet, never the content) in one answer. Every change answers with the rows it created or updated (`TreeChanges`), and deletes answer with what went to the recycle bin, for Undo. `POST /pages` takes an id made by the browser, so a page created offline keeps it.
- **Saving content** (`PUT /pages/:id/content`). Each page has an integer `revision`; a save names the `baseRevision` it started from. If that is still the page's revision, the save is taken in one transaction and the revision goes up by one. If not, the answer is `409 revision_conflict` with the server's revision and content, and the browser merges (D25). Content equal to what is stored always succeeds, so a save repeated after a lost answer is harmless.
- **Versions** (`page_versions`, D33). The versioning hook keeps the text a save replaces, at most every 10 minutes (`auto`), and always when a save settles a conflict. `POST /pages/:id/versions` keeps the browser's side of a conflict it couldn't merge (`conflict`), the page as it is when an edited page is closed (`auto`) or by hand (`manual`, optionally named); a snapshot equal to the last version is skipped. `GET /pages/:id/versions` lists them (without content), `GET …/versions/:vid` reads one, `PATCH` names it, `POST …/restore` makes it the page again (keeping the page as it was, `restore`), `POST …/copy` makes a new page from it after the original. `retention.ts` picks which to keep; the maintenance job thins them.
- **Recycle bin** (`GET /trash`, `POST /trash/restore`, `/trash/restore-to`, `/trash/delete`, `/trash/empty`). Lists each deleted root with its old location, the pages that went with it, when it goes, and whether its place still exists; restores it there or into a chosen section, notebook or group; deletes for good with its versions. `purgeExpired` does the same for roots older than `MEMORA_TRASH_DAYS`, and `assets/cleanup.ts` then deletes files no page or version refers to (after a day's grace).
- **Tags** (`tags`, `page_tags`). Names are unique per user whatever their case. `PUT /pages/:id/tags` sets a page's tags by name and makes new ones; `PATCH`/`DELETE /tags/:id` rename, colour and delete. Pages carry their tag ids, and the tree the user's tags.
- **Links** (`page_links`, D37). Every content change rebuilds the page's list of linked titles (`linkedTitles` in `@memora/shared`). `GET /pages/:id/backlinks` resolves them by title. Renaming a page rewrites the links to it (`renameLinks`) in the same transaction and announces the changed pages. Pages from before Phase 8 are indexed once at startup (`notes/links.ts`).
- **Templates** (`templates`, `notes/templates.ts`). The built-in ones come from `@memora/shared`; users' own are rows, with `GET/POST/PATCH/DELETE /templates`.
- **Rich pages** (D30). Their content is TipTap JSON; a save or conversion that isn't a document is refused (`invalid_content`). `richToText` in `@memora/shared` gives the plain text for snippets and search.
- **Conversion** (`POST /pages/:id/convert`). The browser converts the content; the server checks the base revision, keeps the old content as a `conversion` version, and changes the type and content in one transaction. Other browsers hear about it as `page.updated`.

## Search (`apps/server/src/search`, `routes/search.ts`, D36)

- **Index.** `fts_pages` (FTS5: title, body, tags), keyed by `page_search.docid`, with triggers on `pages`, `page_tags` and `tags` that update it in the same transaction as every change (migration `0006_search.sql`). Deleted pages stay indexed until purged and are filtered out by the query.
- **Queries.** `parseSearch` in `@memora/shared` splits words, `"phrases"`, `-exclusions`, `tag:` and `in:`; words become prefix queries. Filters (notebook, section, tag, type, edited since) are SQL conditions around the match. Ranking is `bm25(10, 1, 4)`, times 1.3 for pages in the user's recent list. Titles are highlighted and snippets cut by FTS5 itself, with control characters as markers.

## Files (`apps/server/src/assets`, `routes/assets.ts`)

- **Upload.** `PUT /api/v1/assets/:id?name=…` takes the file as the request body, whatever its type (the route has its own content-type parser), up to `MEMORA_MAX_UPLOAD_MB`. The id comes from the browser (D28); the same id with the same bytes again is a no-op, so a retried upload is harmless, and another user's id is refused.
- **Storage.** `assets` holds one row per id (name, type, size, image width and height); `asset_blobs` holds the bytes once per user and SHA-256, so the same screenshot pasted twice is stored once.
- **Types.** `assets/image.ts` reads the type and size of PNG, JPEG, GIF, WebP and AVIF from the first bytes; a file only claiming to be an image is stored as plain bytes.
- **Web images** (`assets/fetch.ts`, D31). `POST /api/v1/assets/fetch` downloads an image from the web into a new file: http(s) only; every address the host resolves to is checked against private, loopback, link-local, multicast and other special ranges (IPv4-mapped IPv6 is refused outright); the connection is pinned to the checked address; at most three redirects, each checked; 10 s and 20 MB (or the upload limit) in all; only real images are kept. At most two downloads run at once, as each is held in memory until stored.
- **Download.** `GET /api/v1/assets/:id` answers inline only for those images; anything else is `Content-Disposition: attachment`, with `nosniff` and a sandboxing `Content-Security-Policy`. An id always names the same bytes, so the answer is cacheable for a year (`private`, with an `ETag`).

## Import and export (`apps/server/src/transfer`, `routes/transfer.ts`, D39–D41)

- **Jobs** (`jobs.ts`). `POST /exports` and `POST /imports` start a background job and answer `202` with it; jobs run one at a time, in memory, and publish `job.updated` (at most four times a second) to the user's browsers. `GET /jobs` and `GET /jobs/:id` read them; `GET /jobs/:id/download` answers an export's file, kept in `<data>/tmp/jobs/<id>` for a day (the maintenance job deletes older ones, and startup clears the folder).
- **What an export contains** (`collect.ts`). The notebooks, groups, sections and pages of a scope (page with its subpages, section, group, notebook or everything), read without their content; each page's content is read when its file is written, so a large export holds one page at a time. Files are streamed into the zip (`zip.ts`, yazl), which records each entry's SHA-256 as it goes.
- **`.memora` archives** (`archive.ts`, [FILE_FORMAT.md](FILE_FORMAT.md)): JSON, Markdown and rich documents (also as HTML), files stored once by SHA-256, tags, templates and optional history, then the manifest; encrypted with the backup envelope when a password is given.
- **Markdown folders** (`markdown.ts`): readable names (`safeFileName`, `uniqueNames`), front matter, relative file links, and a loss report for rich pages converted to Markdown.
- **Imports** (`importer.ts`). The body is streamed to disk (up to `MEMORA_MAX_IMPORT_MB`); a `.memora` archive's password comes in the `X-Memora-Archive-Password` header, never in the address, and the logs redact it. Encrypted files are decrypted to the job's folder; the zip is read entry by entry with limits on count and size (`ZipLimitError`). An archive's manifest, format version and every SHA-256 are checked before anything is stored. Files go in first; then everything else in one transaction, with new ids, after what is there. Pages' text waits on disk meanwhile, so memory holds one page at a time. Importing into an existing notebook takes a `pre-import` backup first. Zips without a manifest are read as Markdown folders.
- **PDF** (`pdf.ts`). With `MEMORA_GOTENBERG_URL`, `POST /exports/pdf` sends the browser's printable HTML to Gotenberg with the user's images inlined and a content security policy that blocks every other request; `GET /exports/options` tells the browser whether it can offer this.

## Kanban (`apps/server/src/kanban`, `routes/kanban.ts`, D42)

- **Tables** (migration `0007_kanban.sql`). `projects` (a unique key per user and the next card number), `labels` per project, `boards` (lane mode in `settings_json`), `board_columns` (colour, WIP limit and whether it is strict, Done flag, collapsed, sort), `swimlanes`, and `cards` with `card_labels`, `checklists` and `checklist_items`, `card_comments`, `card_pages` (linked notes), `card_attachments` and `card_activity`. Everything has its owner, and another user's ids are simply not found.
- **Order.** Siblings sort by `sort_key`; a card's key orders it in its column, whatever its lane. Moves name the item they go before (`beforeId`, or null for last).
- **Rules** (`service.ts`). A strict, full column refuses cards (`409 wip_limit`); moving into or out of a Done column completes or reopens a card, and so does making a column a Done column. A card moved to another project takes that project's next number and leaves its labels behind. Changes are written to the card's activity log. Everything a card holds (checklists, comments, linked notes, files) is changed by its own route, which answers the whole card as it is afterwards.
- **Card keys.** `GET /cards/by-key/WEB-42` finds a card for a link in a note.
- **Search.** `fts_cards` (title, key and description, kept by triggers) is searched with the pages when `cards=1`.
- **Events.** Changes publish `projects.changed` (projects, boards, labels: the navigation) or `board.changed` (with the board, and the card when it was one) to the user's other browsers.
- **Archives** (`transfer/kanban.ts`). An export of everything adds a file per project and per board; importing gives new ids and a free key when one is taken ([FILE_FORMAT.md](FILE_FORMAT.md#kanban)).

## Live events (`apps/server/src/events`, `routes/events.ts`)

- **Channel.** `/api/v1/events` is a WebSocket (`@fastify/websocket`), opened with the session cookie and checked for origin like any change. `events/hub.ts` keeps the open sockets per user, in memory, and only ever sends a user their own events.
- **Messages.** Routes that change the tree declare `config.emits: 'tree'`, and an `onResponse` hook publishes `tree.changed` once they have succeeded; a content save publishes `page.updated` with the page's row and new revision. Browsers name themselves with a random id in the `x-memora-device` header (the `device` query parameter for the WebSocket), and an event is not sent back to the browser that caused it.
- **Presence.** Each browser reports the pages it has open (at most 50); the hub sends the user's other browsers a `presence` list with a label per device, such as "Firefox on Windows".
- **Limits.** A heartbeat every 30 s closes dead sockets and those of sessions that ended; more than 60 messages between two heartbeats closes the socket (1008). When the session ends, or must first set a new password or two-step verification, the socket closes with 4401 and the browser stops reconnecting. It then asks `/auth/me` which it was: signed out, or a set-up to do first (syncing pauses until the notes are opened again).
- **Reverse proxies** must pass WebSocket upgrades (see SETUP.md). Without them Memora still works: the browser checks for changes every 30 s instead.

## Web app (`apps/web`)

- **Stack.** React 19 with TanStack Router (routes in `src/router.tsx`) and TanStack Query for server state.
- **Session** (`src/auth/`, `src/lib/api.ts`). `GET /api/v1/auth/me` tells the app whether setup is needed, who is signed in, and the CSRF token. Route guards (`beforeLoad`) send people to setup, login or the forced password change, and after login back to the page they wanted, but only to a path in this app. The API client adds the CSRF token to changes, and when the server says the session is gone, the app forgets its cached data and shows the login page. The admin pages are split into their own chunks. Small UI state (the shell layout, appearance, toasts) lives in zustand stores. Radix primitives provide accessible behaviour for menus, dialogs, popovers, tooltips and selects; the styling is our own.
- **Design tokens** (`src/styles/tokens.css`). Every colour is a CSS variable written with `light-dark()`, so a theme switch only changes `color-scheme` on `<html>` (`data-theme`). `data-glass="off"`, or the system setting for reduced transparency, replaces the translucent panels with solid ones. Tailwind v4 (`src/styles/index.css`) maps the tokens to utilities and switches off its default palette.
- **Section colours** (`src/theme/sections.ts`). The 12 colours are OKLCH hue and chroma pairs. Any element with the `hue` class and `--h`/`--c` gets a matching set of tints (`--sec`, `--sec-soft`, `--sec-ink`). The app accent follows the open section, with an animated transition.
- **Shell** (`src/shell/`). One grid whose columns follow **container queries** on the app root, not the viewport: phone (bottom navigation and drill-down), tablet (icon rail and overlays), desktop (three columns), wide (plus the inspector) and ultra-wide (with the workspace: up to three panes beside the main one). The address says where you are (`/n/`, `/g/`, `/s/`, `/p/` plus an id); `location.ts` turns it into the open notebook, section and page, and on larger screens falls back to the last section and page you had open. Commands (`commands.ts`) are shared by buttons, context menus, the command palette and the keyboard shortcuts (`shortcuts.ts`, one table that also drives the `?` sheet).
- **Workspace** (`src/workspace/`, D44). From 1920 px, panes sit beside the main pane (which stays the address's): one on wide screens, up to three on ultra-wide ones. `model.ts` holds the rules as pure functions (adding and closing panes and tabs, moving and splitting tabs, resizing, layouts); `store.ts` keeps each device class's workspace in local storage, per user; named layouts go in the UI state. `Workspace.tsx` draws the row of panes, their tabs, the dividers and where a dragged tab would land (`tabDrag.ts`); `PaneContent.tsx` shows a page, a board (`BoardView` with its own open card), a search, or the backlinks or history of the main page. The Layout menu in the top bar saves and applies named layouts.
- **Readable width.** The page body sets `--measure` from the longest line in the editor settings (or `none` for a page shown at full width, a list in the UI state); the Markdown source, the preview and rich pages stop there, centred.
- **Notes data** (`src/notes/`). The tree is one TanStack Query entry; `model.ts` builds lookups and ordered lists from it once per change, and plans moves with the same rules and sort keys as the server. Every change shows at once and is then replaced by the server's answer; requests go out one at a time, in order, and each answer is laid under the changes still waiting, so an earlier answer never undoes a later change. A failure shows a toast and reloads the tree. UI state (last section and pages, expanded items) is saved a moment after it changes.
- **Drag and drop** (`src/lib/dnd.ts`). A small pointer-events module instead of a library: drop targets are `data-drop-*` attributes found under the pointer, so rows register nothing. Touch drags start after a long press; Escape cancels. `shell/dropRules.ts` decides what may be dropped where.
- **Saving and sync** (`src/sync/`, D24–D25). The engine starts after login, with one IndexedDB database per user (`store.ts`, through `idb`). Each page has a record: its text, the revision and text it is based on, and whether it waits to be sent; the outbox is simply the records with unsent changes, plus pages created offline.
  - **`doc.ts`**, a page open in a tab. The editor reports every change; within 300 ms the text is in the store, and a second after the last keystroke (or every 5 s while typing goes on) the leader is asked to send it. Changes that reach the record from elsewhere come back into the editor, merged with anything not stored yet.
  - **`engine.ts`**, one per tab. Tabs share the store and a `BroadcastChannel`; a Web Lock picks the leader, which sends and keeps the WebSocket. It also keeps the last tree and settings for starting offline, and the 100 most recently opened pages. On `pagehide`, text not yet in the store goes to local storage, and the next start puts it back.
  - **`sender.ts`** sends the outbox: offline changes to the tree first, then content. A `revision_conflict` is merged with the text both sides started from (`merge.ts`: `node-diff3`, lines first, then word by word). What can't be merged is kept on the server as a `conflict` version and shown as a conflict; a page deleted elsewhere keeps its text as a new page in the Inbox. Retries wait 1 s, doubling to 30 s, with jitter.
  - **`live.ts`**, the WebSocket client: after two failed connections it polls every 30 s while it keeps trying.
  - **After a restore** (D35). The store remembers the server's data id (`MeResponse.dataId`, and the channel's first message, `hello`). When it changes, the tab reloads, and on start the store drops unchanged pages, the kept tree and settings, and unties changed pages from their revisions, so they are compared with the restored pages afresh.
  - **Compare** (`compare.ts`). A conflict opens side by side: Markdown line by line, rich pages block by block; the user picks a side, or both, per change.
  - **`hooks.ts`** turns the state into what the save indicators show. "Saved" appears only once the server has confirmed the latest text, and nothing is shown until the engine has checked what waits to be sent.
  - If IndexedDB can't be used, a store in memory takes over, the tab saves directly, and the app warns that closing the tab could lose changes.
- **Markdown** (`src/markdown/`, D27). `pipeline.ts` is the unified pipeline (GFM, footnotes, alerts, maths, wiki links, front matter, raw HTML, then `rehype-sanitize`); block elements get `data-line`. It runs in `render.worker.ts`, which sends back the tree with positions only on top-level blocks. `Preview.tsx` renders each top-level block on its own (memoised by its source), with components for code (Shiki, `highlight.ts`), maths (`math.ts`, KaTeX), diagrams (`mermaid.ts`), images and files (`asset:` links, from this device's copy while they wait to be sent), wiki links and task boxes. `outline.ts` reads headings and counts words from the source.
- **Editor** (`src/editor/`). `MarkdownPage.tsx` is the page: toolbar, Source / Split / Preview, scroll sync (`scrollSync.ts`, with block positions cached until the preview changes), the outline and the grid editor. `MarkdownEditor.tsx` sets up CodeMirror 6, with settings in compartments so a change needs no new editor. Beside it: the highlight theme (`theme.ts`), table alignment and commands (`tables.ts`, on the shared `table.ts`), formatting commands, slash commands and `[[` suggestions (`completion.ts`), paste and drop (`paste.ts`), image thumbnails and two-column boxes for wide characters (`thumbnails.ts`, `wide.ts`). All of it is one lazily loaded chunk.
- **Rich text** (`src/rich/`, D30–D32). `schema.ts` is the list of nodes and marks (TipTap's, plus callouts, file cards, images with width, alignment and caption, line spacing and cell colours), used by the editor and by conversion alike. `RichEditor.tsx` keeps the document in step with the sync engine like the Markdown editor (the text is the JSON), and handles paste and drop: files become images or file cards, pasted HTML is cleaned (`clean.ts`) and its web images are downloaded by the server afterwards (`files.ts`). Around it: the Word-like toolbar (`RichToolbar.tsx`, which measures its width to drop the tabs and move tools into "More"), `/` and `[[` menus (`suggestions.ts`), drag handles (`dragHandle.ts`), Shiki colours for code (`codeHighlight.ts`, as decorations), image and file views (`views.tsx`), and the page (`RichPage.tsx`: selection menu, link and formula dialogs, the right-click table menu, the A4/Letter sheet, the outline, and the toolbar above a phone's keyboard). `convert.ts` turns Markdown into a rich document through the preview's pipeline; the other way is `richToMarkdown` in `@memora/shared`. The editor is a lazily loaded chunk; PageBody picks it from the page record's type.
- **Files** (`sync/engine.ts`). `addFile` keeps a pasted file as an `uploadFile` op in IndexedDB and answers a new id; the sender uploads ops before page content. Where IndexedDB can't keep Blobs (Safari's private windows), the op keeps the file's bytes instead. Images can be made smaller first (`lib/images.ts`, an Editing setting). The service worker keeps loaded files in `memora-files`, emptied when the user signs out.
- **Search, tags and links** (`src/search/`, `shell/PageTags.tsx`, D36–D37). `SearchView.tsx` is `/search`: the query and filters live in the address, results come 150 ms after typing stops, and without a connection titles are searched on the device. With nothing typed it shows recent pages and the tag browser. Links to pages preview their page on hover (`markdown/PageCard.tsx`; `rich/LinkPreview.tsx` in the rich editor), rich pages mark links to missing pages with a decoration (`rich/wikiLinks.ts`), and the inspector lists backlinks.
- **Favourites, recent pages and templates** (`notes/places.ts`, `shell/Places.tsx`, `templates/`, D38). Both lists are kept in the UI state. "New page ▾" (`shell/NewPageMenu.tsx`), a section's default template and `/template` fill a template in (`contentFor`, converting between Markdown and rich text when needed).
- **Find and replace** (`rich/find.ts`, `rich/FindBar.tsx`). A ProseMirror plugin keeps the matches (found per text block, across formatting) as decorations; the Markdown editor uses CodeMirror's search panel.
- **History and recycle bin** (`src/history/`, D33). `HistoryDialog.tsx` lists a page's versions by day and shows one as it reads (`VersionView.tsx`: Markdown through the preview, rich pages through TipTap's `generateHTML` and DOMPurify), what changed since the one before, or against the page now (`diff.ts`: jsdiff lines, then words). `TrashView.tsx` is the `/trash` screen. Both are lazily loaded; neither is kept offline. The admin Backups page is `settings/BackupsPage.tsx`.
- **Import and export** (`src/transfer`). The export dialog starts server jobs (`.memora`, Markdown) and follows them through `job.updated` (checking every 1.5 s too); the job panel (`TransferStatus`) shows progress and downloads the file when it is ready. Word, HTML and PDF are made in the browser from the pages as rich documents (`document.ts`; Markdown pages through `markdownToRich`): `docx.ts` writes Word with the `docx` library, `print.ts` a print stylesheet that Paged.js lays out in a frame for the preview. Single files (Markdown, text, Word through mammoth, HTML) become pages in the browser (`importFiles.ts`), read like pasted HTML; `.memora` and zip files go to the server. Files can be dropped on the page list and on section tabs (`drop.ts`).
- **Kanban** (`src/kanban/`, D42–D43). `api.ts` holds the queries (projects, a board, a card, a note's cards) and the changes, each shown at once and put back with a message if the server refuses it; events refetch what changed. `model.ts` lays a board out (lanes, columns, filtered and sorted cells) and plans moves, including the priority or label an automatic lane gives. `BoardView.tsx` is `/b/:id`: header, filters and chips, the grid of columns and lanes, quick add, the keyboard (arrows move the focus, Ctrl/Cmd+Shift+arrows move the card, Ctrl/Cmd+Z undoes) and, on phones, one column per screen. `drag.ts` drags cards, columns and lanes by pointer: the target comes from the pointer's position over the columns, the dragged copy moves by transform outside React, and the dragged card stays in the page, hidden, so a finger's touch events keep coming. `CardPanel.tsx` is the card beside the board (a sheet on phones); `LinkNoteDialog.tsx` links notes (N from the panel, recent notes first). Card keys in notes become links through a remark plugin in the Markdown pipeline and a decoration in rich pages (`rich/cardKeys.ts`), for the keys of projects that exist (`keys.ts`).
- **Installed app** (`public/`, `sync/worker.ts`, `sync/keepAll.ts`, D46). `manifest.webmanifest` with icons and iOS splash screens (`scripts/icons.mjs` draws them from the logo with Playwright's Chromium). When a new service worker has installed while an older one controls the page, the app offers "Reload", which tells the waiting worker to take over and reloads; other tabs are told to reload too. Settings → This device turns on keeping every page: `keepAll.ts` fetches the pages the store lacks or has in an older revision, one tab at a time (a Web Lock), in the background, and the engine then keeps them all instead of trimming to the 100 most recent.
- **Service worker** (`sw/`, D26). `sw/plugin.ts` writes the list of built files into `sw.js` at build time: everything the app loads, and whatever those scripts import directly, but not the optional parts loaded on demand (diagrams, maths in the preview, Shiki, conversion). Navigations try the network first and fall back to the kept app after 3 s or offline (or to `offline.html`, when not even the app is kept); hashed assets come from the cache; the API is never touched. It is registered in production builds only.
- **Components** (`src/components/ui/`). Shared building blocks with keyboard support and ARIA roles built in: section tabs (roving focus), the page tree (tree keyboard pattern; for long lists it builds rows as they scroll into view, behind a gap of estimated height, so a section with a thousand pages opens quickly), the command palette (combobox), the split pane (separator) and the save indicator (announces only offline and conflict).
- **Gallery** (`gallery.html`, `src/gallery/`). Shows every component. It is served by the dev server and included only in the `vite build --mode gallery` build that the Playwright tests use, never in the production build.
- **Tests.** Vitest with jsdom for units and components (`*.test.ts(x)` next to the code; `fake-indexeddb` for the store). Playwright in `e2e/` for screenshots, axe accessibility checks and behaviour in a real browser, always in the pinned Playwright image so the pixels match CI. The tests talk to a fake server in the browser (`e2e/helpers.ts`, `e2e/notes.ts`, `e2e/kanban.ts`), which can go down, lose answers, answer slowly and act as a second device. The resilience suite (`e2e/resilience.spec.ts`) and pasting screenshots (`e2e/paste.spec.ts`) run in Chromium, Firefox and WebKit. Speed (`e2e/perf.spec.ts`, a 500-card board) is measured last, on its own (the `perf` project). `e2e/layouts.spec.ts` checks every breakpoint at display scalings from 100 % to 200 %, and `e2e/a11y.spec.ts` walks the app with the keyboard. CI also checks the initial JavaScript against its budget (`scripts/bundle-size.mjs`, 300 KB gzipped).
