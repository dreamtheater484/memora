# Diagram editor: implementation plan (0.9.6)

## Executive overview

Memora 0.9.6 makes diagrams a first-class part of both kinds of page. You draw them in a visual editor, and nobody has to learn Mermaid to use it.

**What you get**

1. **Diagrams appear as drawings everywhere**, never as code:
   - in rich text, as a block like an image: resize it, align it, give it a caption;
   - in the Markdown source view, drawn in place of their code, and in the preview;
   - in page history;
   - in Word, PDF and HTML exports.

   Today rich text pages and exports show Mermaid code instead.

2. **A visual diagram editor**, the same one for both kinds of page, where you work on the diagram itself:
   - **Flowcharts:**
     - click a box to rename it;
     - **+** on a box adds a connected one;
     - drag a box onto another to connect them;
     - click an arrow to label it, restyle it or remove it;
     - shapes, colours, groups and direction.
   - **Mind maps:** type an outline; `Tab` and `Shift+Tab` change the level.
   - **Sequence diagrams:** participants and messages as lists, reordered by dragging.
   - **Timelines, Gantt charts and pie charts:** small tables.
   - **Every other Mermaid diagram type:** code with a live preview and examples.
3. **A gallery of templates** to start from: `/diagram` in either kind of page.
4. **Memora's own look:** its section colours, its font, and rounded shapes with a soft shadow, in light and dark; mind maps as a tidy tree either side of their centre, each branch in its own colour. Exports are always light.
5. **Pages stay portable:**
   - In a Markdown file a diagram is an ordinary ` ```mermaid ` block, so GitHub and other Markdown apps draw it too.
   - Rich text pages store the same text, so converting between the two kinds of page keeps every diagram.
   - Older versions of Memora show the code rather than losing anything.

**One thing it doesn't do:** place boxes by hand. Every diagram is laid out by itself (by Mermaid, and mind maps by Memora's own tidy tree layout), which keeps diagrams tidy with no effort. You steer the layout with the direction, the order of items, and groups.

**How it's built**

- **No database change and no new server code.** A diagram is the code block Memora already stores, plus an optional width, alignment and caption in rich text.
- **A shared model for each diagram type** in `@memora/shared`. A parser and a printer turn Mermaid text into something the editor can change and back again. Lines they don't understand are kept exactly as written.
- **Everything runs in the browser.** The editor is loaded only when it is first opened, so the NAS does no extra work and the editor works offline and in the desktop app.
- **One release, 0.9.6,** built in eleven steps, each with its own tests. It is released through the usual PR, CI and Release workflow.

---

## 1. Goals and principles

- **Super easy.** You start from a template and add, rename and connect with the mouse or the keyboard. Nothing you do needs Mermaid syntax.
- **Graphically brilliant.** One consistent theme that matches Memora, with crisp vector drawings in the app, the PDF and the HTML, and a sharp image in Word.
- **One diagram, two kinds of page.** The same editor, the same look and the same stored text in Markdown and rich text pages.
- **Never lose a diagram.** Code the editor doesn't fully understand is kept as written. Diagrams in pages written by 0.9.5 or older open as they are. An older Memora shows the code instead of dropping it.
- **Light on the NAS.** Rendering and editing happen in the browser, the heavy code loads only when needed, and the caches are bounded.

**Not in this release**

- Free-form drawing, a whiteboard or placing boxes by hand.
- Visual editors for class, state, ER and the other less common diagram types (they get code with a live preview).
- Collaborative editing of diagrams.
- Images inside diagram boxes.

## 2. What users see

### 2.1 Rich text pages

- **Inserting a diagram:** **Insert → Diagram**, or `/diagram`, opens the template gallery. Choosing a template opens the editor, and **Done** puts the diagram in the page. Cancelling inserts nothing.
- **The diagram block** behaves like an image:
  - it is drawn at its natural size, at most the width of the text;
  - selecting it shows a small toolbar: **Edit diagram**, size (**Small**, **Medium**, **Large**, **Fit**), alignment (left, centre, right), **Caption**, **Copy as image** and **Delete**;
  - the corner handle resizes it, and the drag handle moves it.
- **Opening the editor:** double-click the block, or select it and press `Enter`.
- **Keyboard:** the arrow keys move over the block as a whole, and `Backspace` or `Delete` removes it when it is selected.
- **No code view in rich text,** except for diagram types that have no visual editor, where code is the editor.
- **Diagram code blocks from 0.9.5 and older** (**/ → Diagram**) become drawn diagrams by themselves. Setting a code block's language to Mermaid turns it into a diagram.
- **A diagram with a mistake** (possible only through code) shows the error in plain words, with an **Edit diagram** button.

### 2.2 Markdown pages

- **The source view draws each ` ```mermaid ` block in place of its code** while the cursor is elsewhere:
  - two buttons sit beside the drawing: **Edit diagram** and **Show code**;
  - moving the cursor into the block with the arrow keys, or choosing **Show code**, shows the code;
  - moving out draws it again.
- **Settings → Editing → Draw diagrams in the source view** turns this off for people who want only text. It is on by default.
- **The preview:** each diagram gets an **Edit diagram** button on hover and on keyboard focus.
- **Insertion:** the toolbar's **Diagram (Mermaid)** item and `/diagram` (also `/mermaid`) open the template gallery. **Done** inserts a fenced block.
- **Writing back:** the editor replaces the block's code in a single change, so `Ctrl/Cmd+Z` undoes a whole editing session. The fence and its indentation stay as they were.
- **A Code tab:** in Markdown pages the editor shows the Mermaid code beside the drawing, and the two stay in step both ways.

### 2.3 The diagram editor

- **Layout:**
  - **desktop:** a full-screen dialog with the diagram in the middle and a side panel on the right;
  - **phone:** a sheet with the lists first, since tapping small boxes is hard.
- **Header:** the diagram's type, **Templates**, **Undo** and **Redo**, and **Done**.
  - `Esc` or **Cancel** asks first when there are changes.
  - `?` lists the editor's keys.
- **Canvas:**
  - the real Mermaid drawing, redrawn as you edit (debounced to about 120 ms);
  - zoom with **Fit**, **+** and **−**, `Ctrl` and the mouse wheel, or a pinch;
  - pan by dragging empty space;
  - a mistake keeps the last good drawing on screen and says what's wrong in plain words.
- **Side panel:**
  - the selected item's properties;
  - for each type, a list of everything in the diagram.

  On a phone this list is how you edit, and it is also the editor's keyboard and screen-reader mode.

- **Undo history** is the editor's own. **Done** writes the result back as one change.

#### Flowcharts

- **Select:** click a box or an arrow, or use the arrow keys.
- **Rename:** double-click, `Enter` or `F2` puts an input over the box; `Enter` confirms and `Esc` cancels.
- **Add:** hovering a box shows **+** handles on its sides; clicking one adds a connected box in that direction and starts editing its label. With the keyboard:
  - `Tab` adds a connected box;
  - `Shift+Enter` adds a box beside it, connected to the same parent.
- **Connect:**
  - drag from a **+** handle to another box;
  - or drag a box and drop it on another.
- **Arrows:** click one to edit its label, choose solid, dotted or thick, choose its arrowheads (end, both, none), or remove it.
- **Shapes:** rectangle, rounded, stadium, circle, decision (diamond), hexagon, input/output (parallelogram), database (cylinder) and subroutine.
- **Colours:** eight from Memora's palette, with a lighter fill and a stronger border. They work in light and dark.
- **Groups:** select several boxes with `Shift`-click or a selection rectangle, then choose **Group** to name the group. Groups can be nested.
- **Direction:** top to bottom, left to right, bottom to top, or right to left.
- **Delete:** `Delete` removes the selected boxes and the arrows on them.
- **Outline list:** boxes with their connections, editable as text rows. This is the phone, keyboard and screen-reader way to edit.

#### Mind maps

- **An outline beside the drawing:**
  - `Enter` adds a topic at the same level;
  - `Tab` and `Shift+Tab` change the level;
  - `Alt+↑` and `Alt+↓` move a topic.
- **Clicking a topic in the drawing** selects its row.
- **Shape per topic:** default, rounded, square, circle, cloud, bang or hexagon.
- **The root** is the central topic.

#### Sequence diagrams

- **Participants:**
  - add one, rename it, and switch between person (actor) and system (participant);
  - drag to reorder.
- **Steps:** a list of rows, each one of these:
  - a **message:** from ▾, arrow ▾, to ▾, text;
  - a **note:** left of, right of or over one or two participants;
  - a **block:** Loop, Alt with Else, Opt, Par or Critical, which indents the rows it holds.

  Rows can be dragged to reorder.

- **Arrow styles:** request, reply (dashed), async, lost (cross) and line.
- **Automatic numbering:** on or off.
- **Clicking a message in the drawing** selects its row.

#### Timelines, Gantt charts and pie charts

- **Timeline:** title, sections, periods with one or more events each.
- **Gantt:**
  - title, sections and tasks;
  - each task has a name and a status (to do, done, active, critical, milestone);
  - it starts on a date or after another task;
  - it has a length or an end date, with date pickers;
  - weekends can be left out.
- **Pie:** title, slices with a label and a value, and an option to show the values.

#### Other diagram types

- Class, state, ER, user journey, quadrant, XY chart, Sankey, block, architecture, Git graph, packet, requirement and C4.
- They get a code editor with highlighting and a live preview, and an **Examples** menu with a starter for each type.

### 2.4 Templates gallery

- **A grid of drawn previews, grouped by type:**
  - **Flowchart:** process, decision, swimlane-style groups;
  - **Mind map:** brainstorm, project outline;
  - **Sequence:** request and response, sign-in;
  - **Timeline:** project milestones;
  - **Gantt:** small project plan;
  - **Pie:** a breakdown.
- **Blank** for each type.
- The same gallery appears in both kinds of page and from the editor's **Templates** button. Applying a template replaces the diagram, after asking.

### 2.5 Exports and elsewhere

- **PDF** (both the browser preview and Gotenberg) **and HTML:** the diagram as vector SVG, centred or aligned as in the page, with its caption. It never splits across pages.
- **Word:** a sharp PNG (drawn at twice the size) with the caption below it and alt text.
- **Markdown export:** the ` ```mermaid ` code, as now. Width, alignment and caption are listed in the conversion's loss report (rich text → Markdown).
- **`.memora` archive:** content as now. The archive's HTML copy of a rich page shows the diagram's code, because the server has no browser to draw it.
- **Page history:** diagrams are drawn. **The conflict screen** compares their code, like any other text.
- **Page snippets and search:** they show the words in a diagram (box labels, messages, topics, tasks) instead of `flowchart LR A --> B`.

## 3. Technical design

### 3.1 Storage and compatibility

- **Markdown:** a fenced block with the info string `mermaid`. This is unchanged.
- **Rich text:** the existing `codeBlock` node with `language: 'mermaid'`. Three optional attributes are added to `codeBlock`:
  - `width`: pixels, null for the natural size;
  - `align`: `left`, `center` or `right`, null for centre;
  - `caption`: a string, null for none.

  They are parsed from and rendered to `data-` attributes.

- **No database migration and no API change.** `parseRich` accepts the document as now.
- **Older clients** (an old tab, a 0.9.5 desktop app reading an exported page):
  - they show a code block, so there's no data loss;
  - if they save the page, the three attributes are dropped and the diagram stays;
  - this is the reason for reusing `codeBlock` rather than adding a new node type, which old clients would strip.
- **Markdown conversion:**
  - `richToMarkdown` writes ` ```mermaid ` as now;
  - the attributes go into a new loss `RICH_LOSSES.diagramLayout = 'Diagram size, alignment and captions'`;
  - `convert.ts` (Markdown → rich) already yields `codeBlock` with `language: 'mermaid'`.
- **`docs/FILE_FORMAT.md`** documents the attributes.

### 3.2 The rendering service (`apps/web/src/diagrams/render.ts`)

It replaces `markdown/mermaid.ts`.

- **One Mermaid instance**, loaded lazily. Mermaid becomes an exact version in `package.json`, because the editor relies on the shape of its SVG.
- **A render queue:** `mermaid.render` isn't safe to run concurrently, so renders run one at a time.
- **An LRU cache** keyed by code, theme and purpose (page, editor or export), with at most 40 entries.
- **Rendering in view:** diagrams in a page are drawn when they scroll into view (IntersectionObserver), so long pages open quickly.
- **The Memora theme:**
  - Mermaid's `base` theme, with `themeVariables` from Memora's OKLCH section hues (converted to hex, which Mermaid needs) for light and dark;
  - Figtree, rounded corners, 1.5 px lines, and tuned spacing and curves, through `themeCSS`;
  - a finishing pass on the sanitised SVG: a soft shadow under boxes and participants, each participant's activations in its own colour, centred mind map words, and the palette's dark versions (§3.3);
  - mind maps laid out by Memora's own tidy tree (the centre in the middle, branches either side, curves that taper), registered in place of Mermaid's force layout, which also spares loading cytoscape.
- **Security:**
  - `securityLevel: 'strict'`;
  - `htmlLabels: false`, so labels are pure SVG text: safe, and drawable onto a canvas for Word;
  - the SVG is sanitised again with DOMPurify's SVG profile;
  - each render gets a unique id prefix, because Mermaid scopes its styles by id.
- **Accessibility:** the SVG gets `role="img"` and a label: the caption, `accTitle`, or a summary from `diagramText` ("Flowchart: Order received, Paid?, Ship, Refund").
- **Exports:** `renderForExport(code)` returns `{ svg, width, height }` in the light theme with Figtree embedded as a base64 `@font-face` in the SVG, so a canvas draws the text in the right font and at the right width.

### 3.3 Colours that travel

- **In the code:** a colour is written as `classDef m-blue fill:#ddf0ff,stroke:#4c94ec,color:#174276` plus `class A,B m-blue`. The colours are Memora's section hues: a soft fill, a stronger edge and dark words. GitHub and other Markdown apps show the same colours.
- **In dark mode:** Memora gives the eight palette colours their dark versions in the drawn SVG. Mermaid writes `classDef` styles as `!important` inline styles, which a style sheet can't override.
- **Classes the user wrote** keep their own colours in both themes.

### 3.4 Shared diagram models (`packages/shared/src/diagrams/`)

These are pure TypeScript with no DOM, unit-tested, and usable by the server for search text.

- **`detect(code)`:** the diagram type from the first statement, skipping front matter, `%%{init}%%` directives and comments.
- **`parse(code)` and `print(model)`** for each supported type:
  - **`flowchart.ts`:**
    - nodes (id, label, shape, colour);
    - edges (from, to, label, line, arrowheads);
    - groups (nested subgraphs);
    - direction;
    - the input forms it reads: chains (`A --> B --> C`), `&` lists, every edge-label form (`-- text -->`, `-->|text|`) and the classic shape syntax.
  - **`mindmap.ts`:** an indentation tree, with a shape for each topic.
  - **`sequence.ts`:** participants and actors with aliases; messages with arrow types; notes; nested blocks with branches; `autonumber`.
  - **`timeline.ts`, `gantt.ts`, `pie.ts`:** as in §2.3.
- **Keeping what it doesn't model:** the parser keeps a line it doesn't model (comments, `click`, `style`, `linkStyle`, `accTitle`, `accDescr`, icons, unknown keywords) as an extra attached to its position. The printer writes it back unchanged.
- **Refusing:** when a construct would change meaning if dropped (for example the new `A@{ shape: … }` syntax, until it is supported), `parse` refuses with a reason naming the line. The editor then opens that diagram in code mode and says why.
- **Printing changes as little as possible:**
  - statements keep their order;
  - new items are added at the end of their section;
  - the printer formats only the lines whose items changed;
  - a diagram opened and closed without changes is written back exactly as it was.
- **Ids:** new box ids are short and stable (`n1`, `n2`, …). Labels are quoted and escaped when needed (`A["Total (net)"]`, `#quot;` for quotes).
- **`diagramText(code)`:** the human words of a diagram, for snippets, search and summaries. Types without a model fall back to quoted strings and labels found by a simple pattern.

### 3.5 The editor (`apps/web/src/diagrams/editor/`)

A lazily loaded chunk.

- **`DiagramEditor`:**
  - the dialog, with a model-or-code state for each diagram;
  - undo and redo over models (with code as text in code mode);
  - live rendering through §3.2;
  - the panels for each type.

  Its props are the initial code, the page kind (Markdown, which has the code tab, or rich), and `onDone(code)`.

- **Linking the drawing to the model:**
  - Mermaid gives each flowchart node an element id like `flowchart-<id>-<n>` and each edge one like `L_<from>_<to>_<n>`, with label groups; sequence and mind-map elements have their own patterns;
  - `hitmap.ts` reads these into a map from SVG elements to model ids, and the canvas draws its selection rings, **+** handles and drop targets over them;
  - tests pin this against the installed Mermaid version (§5);
  - if the map can't be built for an element, that item is still editable through the list.
- **Inline label editing:** an `<input>` positioned over the element's box, scaled with the zoom.
- **Dragging:**
  - pointer events with a threshold;
  - a dragged box shows a ghost;
  - dropping it on a box connects the two, and dropping it on empty space does nothing (Mermaid places boxes).
- **Templates:** `templates.ts` holds a list of `{ type, name, code }`, and the gallery's previews come from the render cache.
- **Code mode:** CodeMirror with a small Mermaid stream highlighter (keywords, arrows, strings, comments) and a live preview, for unsupported types or on request in Markdown pages.

### 3.6 Rich text integration (`apps/web/src/rich/`)

- **`DiagramCodeBlock`:** `StarterKit` with `codeBlock: false`, plus `CodeBlock.extend` adding the three attributes and a node view through `views.diagram`. This follows the pattern used for images.
- **`DiagramView` (React):**
  - used only when `language === 'mermaid'`, and it has no `contentDOM`, so the cursor never enters the hidden code;
  - other code blocks keep the normal view, and `update()` returns false when the language changes, so ProseMirror rebuilds the view;
  - it reuses the image view's resize handle, alignment control and caption field.
- **Commands:** `insertDiagram(code)` and `updateDiagram(pos, code)` (one transaction).
- **Keys:** `Enter` on a selected diagram opens the editor.
- **Elsewhere in rich text:**
  - `slashItems.tsx`: **Diagram** opens the gallery instead of inserting sample code;
  - **Insert** tab: a **Diagram** button;
  - **More** menu: the same.
- **Read-only HTML** (`VersionView`): after sanitising, `<pre><code class="language-mermaid">` elements are replaced by drawings from the service.
- **`codeHighlight.ts`** already skips Mermaid.

### 3.7 Markdown integration (`apps/web/src/editor/`, `apps/web/src/markdown/`)

- **`diagrams.ts`** (new, beside `thumbnails.ts`):
  - a `StateField` of block decorations, found through the Markdown syntax tree (`FencedCode` with `CodeInfo` `mermaid`);
  - when the selection is outside a block, its lines are replaced by a widget holding the drawing and the two buttons;
  - the field updates only the blocks a change touches, and `eq()` compares code and theme, so typing elsewhere doesn't redraw;
  - it is controlled by the new setting `editor.drawDiagrams` (default true), in `editorSettingsSchema`.
- **Show code:** puts the cursor on the block's first code line.
- **Write-back:** dispatches one transaction replacing the text between the fences.
- **`Preview.tsx`:** the `Mermaid` component uses the render service and gets the **Edit diagram** button. `data-line` locates the fence in the source.
- **`commands.ts` and `completion.ts`:** `insertMermaid` opens the gallery, and `/diagram` joins `/mermaid`.

### 3.8 Exports (`apps/web/src/transfer/`, `packages/shared/src/richHtml.ts`)

- **`document.ts`:** `prepareDiagrams(pages)` collects every Mermaid block, renders each once through `renderForExport`, and returns a map. Markdown pages reach it after `markdownToRich`, so they are covered too.
- **`richToHtml(doc, { asset, diagram })`:**
  - the new `diagram(code)` option returns sanitised SVG markup, written as `<figure class="diagram" data-align=…><svg…/><figcaption>`;
  - without the option (the server's archive HTML), the output is `<pre class="diagram-code">`.
- **`print.ts`:** `figure.diagram svg { max-width: 100%; height: auto }` and `break-inside: avoid`.
- **`docx.ts`:** the SVG is drawn onto an `OffscreenCanvas` at twice its size, giving a PNG `ImageRun` sized like the block (at most the text width), with the caption paragraph and alt text. This reuses the image path's `picture()` sizing helpers.

### 3.9 Search and snippets

- **`richToText`** uses `diagramText` for Mermaid code blocks, and so does the Markdown snippet function.
- **The search index** already holds the raw code, so words in diagrams are found today. Pages get the cleaner text the next time they are saved. No reindex is needed.

### 3.10 Accessibility

- **The editor:**
  - every action works from the keyboard;
  - the outline list is a complete editing mode;
  - focus returns to the diagram after **Done**;
  - an `aria-live` region announces additions, connections and deletions;
  - the dialog is labelled.
- **Diagrams in pages:** `role="img"` with a label (§3.2). The caption is a real `figcaption`.
- **Checks:** the axe check runs on the editor and on pages with diagrams.

### 3.11 Performance and memory

- **The NAS:** nothing new runs there. There are no new server dependencies, and the image size and RAM use are unchanged.
- **The browser:**
  - the Mermaid chunk loads on the first diagram (as now), and the editor chunk on the first edit;
  - the render cache is bounded, and diagrams are drawn only when in view.
- **Budgets** (in the e2e performance test):
  - a page with 20 diagrams opens and draws the visible ones in under 1.5 s;
  - the editor redraws a 100-box flowchart in under 300 ms on the CI machine.

### 3.12 Security

- **Mermaid:** `strict` with no HTML labels; `click` directives are never run; the SVG is sanitised a second time.
- **Labels** are escaped by the printer.
- **The CSP is unchanged.** Mermaid's styles live inside the SVG, as today.
- **The desktop app** needs no new permissions.

## 5. Testing

- **Unit tests (shared):**
  - for each type, parse → print round trips over a fixture corpus, including the Mermaid documentation's examples that fall in the supported set;
  - extras kept in place;
  - refusals with their reasons;
  - label escaping;
  - unchanged diagrams written back exactly;
  - `diagramText`;
  - `richToMarkdown` with the diagram loss;
  - `richToHtml` with and without the `diagram` option.
- **Unit tests (web):**
  - the render queue and cache;
  - template code that parses and prints;
  - the editor's model operations (add, connect, group, delete, reorder) for each type.
- **End-to-end tests (Chromium):**
  - building each type with the mouse, and a flowchart with the keyboard only;
  - the stored code after each;
  - the hit map finding every box and arrow under the pinned Mermaid;
  - the rich block's whole life (insert, edit, resize, align, caption, undo, convert to Markdown and back);
  - Markdown drawings, **Show code**, write-back and undo;
  - history drawing diagrams;
  - phone layout editing through the lists;
  - exports: the HTML contains `<svg>`, the Word file contains a PNG of the expected size, and the PDF preview draws it;
  - dark mode;
  - axe checks on the editor and on pages.
- **Visual baselines:**
  - a themed diagram of each supported type, light and dark;
  - the editor with a selected box and its handles;
  - a rich diagram block with a caption;
  - the template gallery.
- **Firefox and WebKit:** drawing and a basic flowchart edit, since SVG measurement differs between engines.
- **Performance:** the budgets in §3.11.
- **The desktop app:** a page with a diagram draws offline in the packaged app.
- **Run locally** in the pinned Playwright image as usual, then in CI and in the release dry run on every system.

## 7. Risks

| Risk                                                             | Effect                                                    | Mitigation                                                                                                                                                               |
| ---------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Mermaid changes its SVG ids or structure in an update            | Clicking boxes stops working in the editor                | An exact Mermaid version; end-to-end tests that the hit map finds everything; the list editing still works without it; upgrades of Mermaid as deliberate PRs             |
| Hand-written Mermaid uses syntax outside the models              | The visual editor can't take it                           | Unknown lines are kept as extras; meaning-changing constructs open in code mode with the reason; the fixture corpus grows with every case found                          |

## 8. Decisions taken in this plan

These can be changed before building starts:

1. **Diagrams are stored as Mermaid text:** the existing code block in rich text and a fenced block in Markdown. This keeps them portable and compatible.
2. **The Markdown source view draws diagrams by default,** with a setting to show only code.
3. **Rich text pages have no code view,** except for diagram types without a visual editor.
4. **Colours are written into the code** as `classDef` and `class` lines, so they travel with the file. Dark mode adjusts them inside Memora.
5. **Word gets a high-resolution PNG;** PDF and HTML get vector SVG.
